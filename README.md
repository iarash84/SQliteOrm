# SQliteOrm

[فارسی](README.fa.md) | English

SQliteOrm is a lightweight, synchronous SQLite micro-ORM for .NET 8. Its current API is instance-based, metadata-driven, strongly typed where practical, and parameterized by default. It is intentionally smaller than a full LINQ provider or Entity Framework.

## Setup and lifecycle

Reference the project and create one `SqliteOrm` instance for each database configuration:

```csharp
using SQliteOrm;

using var db = new SqliteOrm(new SqliteOrmOptions
{
    ConnectionString = "Data Source=app.db",
    EnableForeignKeys = true,
    EnableWal = true,
    BusyTimeout = TimeSpan.FromSeconds(5),
    CommandTimeout = 30
});
```

Each ordinary operation opens and disposes its own connection. A transaction opens one connection and shares it with every operation in its callback. Disposing the ORM prevents new operations; it does not represent a permanently open connection. This makes `SqliteOrm` suitable for dependency injection without requiring a DI framework.

`SqLiteOrm.Initialize/Instance` is retained only as a compatibility facade. New code should construct and inject `SqliteOrm`.

## Entity mapping

```csharp
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

[Table("Users")]
public sealed class User
{
    [Key, AutoIncrement]
    public long UserId { get; set; }

    [Column("email_address"), Required, Unique]
    public string Email { get; set; } = string.Empty;

    public string DisplayName { get; set; } = string.Empty;
    public bool IsActive { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public DateTime? LastLogin { get; set; }
    public string? Nickname { get; set; }
    public UserRole Role { get; set; }
    public byte[]? Avatar { get; set; }

    [NotMapped]
    public string? UiLabel { get; set; }
}
```

Mapping metadata is reflected once per CLR type and cached. `[Key]` is independent of the property name. Composite keys are not supported and are rejected. `[AutoIncrement]` is valid only on an `int` or `long` key. For source compatibility, an integer key named `Id` is also generated by convention; new models should use `[AutoIncrement]` explicitly.

Supported attributes:

| Attribute | Effect |
| --- | --- |
| `[Table]`, `[Column]` | Overrides table or column name. |
| `[Key]` | Selects the single primary key. |
| `[AutoIncrement]` | Emits SQLite `AUTOINCREMENT` and marks an integer key as generated. |
| `[Required]` | Emits `NOT NULL`. |
| `[Unique]` | Emits `UNIQUE`. |
| `[NotMapped]` | Excludes a property from all mapping. |
| `[ForeignKey]` | Emits a foreign key with validated SQLite actions. |

Supported CLR mappings:

| CLR type | SQLite affinity / representation |
| --- | --- |
| `byte`, `short`, `int`, `long`, `bool`, enum | `INTEGER`; bool is `0`/`1`, enums use their underlying value. |
| `float`, `double` | `REAL` |
| `decimal` | `NUMERIC` |
| `byte[]` | `BLOB` |
| `string`, `Guid` | `TEXT` |
| `DateTime`, `DateTimeOffset`, `DateOnly`, `TimeOnly` | `TEXT` in invariant round-trip format. |
| nullable supported value types | Same mapping as the underlying type; database `NULL` becomes `null`. |

There is currently no public custom type-handler registration API. Use supported types or raw SQL with an explicit representation.

## Schema creation and migrations

```csharp
db.CreateTable<User>();
```

`CreateTable<T>()` executes `CREATE TABLE IF NOT EXISTS`; it does not compare or upgrade an existing table. Use migrations for deployed schema changes:

```csharp
using SQliteOrm.Migrations;

public sealed class Migration002_AddNickname : Migration
{
    public override void Up(MigrationBuilder migration) =>
        migration.AddColumn<User>(user => user.Nickname, nullable: true);

    public override void Down(MigrationBuilder migration)
    {
        // Dropping a column requires a table rebuild and is not in the initial DSL.
    }
}

db.Migrate(new Migration002_AddNickname());
```

Migration IDs default to class names, are ordered with ordinal comparison, and are recorded with a UTC timestamp in `__SQliteOrmMigrations`. Each pending migration and its history insert run in one transaction. Successful earlier migrations remain applied if a later migration fails. An ID never runs twice. Run migrations from one coordinated application-startup path; the migration runner is not a distributed deployment lock.

The builder supports `ExecuteSql`, `CreateTable`, `DropTable`, `AddColumn`, `CreateIndex`, `DropIndex`, `RenameTable`, and `RenameColumn`. `RenameColumn` needs SQLite 3.25 or newer. `AddColumn` rejects primary-key, auto-increment, and unique constraints. Drop-column and other table-rebuild operations are deliberately unsupported. `RollbackLastMigration(...)` runs `Down` for the latest supplied applied migration.

## Inserts and upserts

```csharp
var user = new User { Email = "ada@example.com", IsActive = true, Role = UserRole.Admin };
db.Insert(user);

db.Insert(new List<User>
{
    new() { Email = "a@example.com" },
    new() { Email = "b@example.com" }
});

db.Upsert(user, conflictOn: value => value.Email);
```

Insert excludes ignored and generated properties. A generated integer key is assigned back to the entity. Bulk insert uses the transaction infrastructure and rolls back as one unit. Upsert uses one atomic `INSERT ... ON CONFLICT ... DO UPDATE` statement without an existence query. Its target must be a mapped key or unique property; generated and key columns are not updated.

## Strongly typed queries

`Table<T>()` builds state and executes only at a terminal method:

```csharp
var users = db.Table<User>()
    .Where(user => user.IsActive && user.Role != UserRole.Disabled)
    .Where(user => user.Email.Contains("@example.com"))
    .OrderBy(user => user.DisplayName)
    .ThenByDescending(user => user.CreatedAt)
    .Skip(20)
    .Take(20)
    .ToList();
```

Terminal methods are `ToList`, `First`, `FirstOrDefault`, `Single`, `SingleOrDefault`, `Any`, and `Count`. `First` uses SQL `LIMIT 1`; `Any` uses an existence query; `Count` uses `COUNT(*)`. Negative `Skip` or `Take` values are rejected. `ThenBy` requires a preceding ordering. Multiple `Where` calls use `AND`.

Convenience methods include:

```csharp
User? user = db.FirstOrDefault<User>(x => x.Email == email);
bool exists = db.Any<User>(x => x.Email == email);
int count = db.Count<User>(x => x.IsActive);
User? byKey = db.Find<User, long>(42L);
```

### Predicate support

Supported expression constructs are:

- `==`, `!=`, `>`, `>=`, `<`, `<=`
- `&&`, `||`, unary `!`
- `x == null` and `x != null`
- boolean mapped properties
- `string.Contains`, `StartsWith`, and `EndsWith`
- captured or constant collections with `Contains`, translated to `IN`
- constants, captured fields, nullable values, enums, and grouping

All runtime values become SQLite parameters. LIKE wildcard characters are escaped. Arithmetic, navigation chains, computed selectors, arbitrary method calls, string-comparison overloads, and arbitrary expression evaluation are unsupported and throw `NotSupportedException`. Use parameterized raw SQL when the expression DSL cannot represent a query.

## Updates and deletes

Entity update uses the mapped key:

```csharp
user.DisplayName = "Ada Lovelace";
db.Update(user);
```

Partial update changes selected columns without loading entities:

```csharp
int affected = db.Update<User>()
    .Set(x => x.IsActive, false)
    .Set(x => x.LastLogin, null)
    .Where(x => x.LastLogin < cutoff)
    .Execute();
```

Partial update requires at least one `Set` and one `Where`, parameterizes every value, rejects ignored or database-generated properties, and returns the affected-row count. There is no implicit full-table update.

```csharp
int deleted = db.Delete<User>(x => !x.IsActive && x.LastLogin < cutoff);
int allDeleted = db.DeleteAll<User>(); // deliberately explicit
db.Delete<User, long>(userId);
```

Predicate delete always requires a non-null predicate. `DeleteAll<T>()` is the explicit full-table operation.

## Typed inner joins

```csharp
var results = db.Table<Order>()
    .Join<Customer>(order => order.CustomerId, customer => customer.CustomerId)
    .Where((order, customer) => customer.IsActive)
    .Select((order, customer) => new OrderSummary
    {
        OrderId = order.OrderId,
        CustomerName = customer.Name
    })
    .ToList();
```

Table and column names come from metadata and filter values are parameters. The current API supports one `INNER JOIN`, joined filtering, and member-initializer projection. LEFT JOIN, join chains, aggregates over joins, and arbitrary projection expressions are not implemented.

## Transactions

```csharp
db.Transaction(tx =>
{
    tx.Insert(order);
    tx.Update(customer);
    tx.Execute("INSERT INTO Audit (Message) VALUES (@message)", new { message = "created" });
    var count = tx.ExecuteScalar<int>("SELECT COUNT(*) FROM Orders");
});
```

The callback uses one connection and one SQLite transaction. It commits only after the callback succeeds. On failure, rollback is attempted and the original exception is rethrown. The session becomes invalid when the callback ends. Nested transactions are explicitly rejected; bulk operations reuse an active transaction instead of creating another one.

## Raw SQL

Raw SQL is the escape hatch, not a replacement for the typed query DSL:

```csharp
var users = db.Query<User>(
    "SELECT * FROM Users WHERE IsActive = @active AND CreatedAt >= @since",
    new { active = true, since });

db.ExecuteNonQuery(
    "UPDATE Users SET DisplayName = @name WHERE UserId = @id",
    new { name, id });

int total = db.ExecuteScalar<int>("SELECT COUNT(*) FROM Users");
```

Anonymous-object public properties are cached as parameter metadata. Dictionaries remain supported for dynamic parameter sets. Names may include or omit `@`; empty, invalid, or duplicate normalized names are rejected. Nulls, enums, and mapped CLR values use the centralized converter. Values are passed to `SQLiteCommand`; they are never interpolated or replaced in SQL text. SQL identifiers and SQL structure remain the caller's responsibility.

Result columns map case-insensitively to writable mapped properties. `ExecuteScalar<T>` returns `default` for SQL `NULL`.

## Threading, concurrency, and SQLite behavior

- An ORM instance does not share ordinary-operation connections; reads use independent connections.
- Writes on one instance are serialized by an internal lock. Different instances are not coordinated by that lock and rely on SQLite locking, busy timeout, and WAL settings.
- A transaction holds the instance write lock for its callback and uses an `AsyncLocal` transaction context. The public API is synchronous; there are no async query or command APIs.
- Do not dispose an instance while other callers are using it. Disposal and concurrent use are not a supported race.
- SQLite still permits only one writer at a time. WAL improves reader/writer coexistence but does not remove write contention.
- In-memory SQLite databases are connection-scoped; because ordinary operations open separate connections, use a file database for multi-operation workflows.
- There are currently no logging, interceptor, hook, or public custom-converter extension points.

## Errors and compatibility APIs

Invalid selectors and unsupported expressions fail early with `ArgumentException`, `InvalidOperationException`, or `NotSupportedException`. Provider failures remain `SQLiteException` and retain provider details. The library does not silently evaluate unsupported predicates or insert values into SQL.

The canonical API is the instance-based `SqliteOrm`, `Table<T>()`, typed joins, predicate deletes, partial update builder, and anonymous-object raw parameters. The following remain for source compatibility but are not recommended for new code:

- `SqLiteOrm.Initialize/Instance`
- dictionary-based `GetAll`, condition, ordering, and relation APIs
- string/tuple relation APIs
- property/value `FindOneByKey`, `Exists`, and `Delete`
- the older Upsert argument order

They delegate to current metadata and command infrastructure where practical. Removing or renaming these public members, the `SQliteOrm` namespace/package capitalization, and the integer-`Id` auto-generation convention requires a future major version.

## Scope summary

SQliteOrm is synchronous and SQLite-specific. It does not implement `IQueryable<T>`, change tracking, lazy loading, navigation loading, composite keys, async APIs, distributed migration locking, arbitrary projections on single-table queries, custom converters, or a full migration/table-rebuild engine. Prefer its typed APIs for supported operations and safe parameterized raw SQL for the rest.
